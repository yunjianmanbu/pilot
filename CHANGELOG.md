## [1.0.6] - 2026-11-24

1.0.6 fixes one thing only: not being able to tell whether a long task is still working. A task that has been running for minutes used to show three blinking dots and the word running, with no way to tell a fresh start from a stuck run — it now reports on four fronts at once: the top-bar pill shows step N and a stopwatch counted from the start, the waiting row follows "working on step N" with the same clock, the clock stays once text has begun to stream but the run is still going, the running process box and each tool card carry their own seconds, and past 45 seconds the label gains "still working". All of these numbers tick in the renderer once per second: they never reach the main process, never issue a request and never cause a model call or cost a token; the prompt only loosens one line — say what a long action is going to do before it starts and what it returned afterwards — while the ban stays on filler chatter, not on that note. The pairing dialog is now accurate: its device row says in one place who is asking, from which address and how long is left, the countdown is its own chip that no longer jumps as the text changes, and the last 15 seconds turn urgent; a browser page reaches the app over the /bridge channel and can only act as the host, so the old client-user option, which left the page with no channel to the main process and an empty shell, is gone — the fixed role is stated instead and the button reads Allow access. The two permanent status lines at the bottom of the sidebar (model name, running count) are gone, because both already live in the bottom-left resource strip and the top-bar pill. This round Windows is at 1.0.6, macOS stays on 0.1.90, Linux stays on 0.1.82, and the CLI and source packages stay on 0.1.76.

- The top-bar running pill shows step N and how long it has run, and the waiting row, process box and tool cards carry the same clock
- All of it is local renderer timing: no new IPC, request, model call or token
- Past 45 seconds the label adds "still working", and it stays hidden under three seconds so it never flashes
- The pairing dialog's device row carries the source and the countdown together, and the last 15 seconds turn urgent
- A browser visit is fixed to the host role (the /bridge channel only accepts host identity), so the client option that could never work is gone
- The two permanent status lines at the bottom of the sidebar are gone; that information lives in the bottom-left resource strip and the top-bar pill

## [1.0.5] - 2026-11-24

1.0.5 finishes the places that were on but did not behave as if they were. The Settings dialog used to be sized by its content, so on a wide screen it stayed a narrow column and fields wrapped onto two lines — it now opens at 1120 pixels with a window-following height, the section list and the form scroll independently, and whatever you were filling in survives a section switch. Contrast and saturation are gone from Appearance: they retuned the same palette the themes already cover, so theme, font size and interface language remain. Ending a command no longer takes other applications with it — the old code ended the whole process tree, and when a Word document you had open and were writing happened to sit in that tree it was closed too, which is why a command run kept closing and reopening Word; now only the command's own process ends, then its descendants one by one, and your Word stays open. The web service switch now means what it says: with it off, the root page, the pages and the credential endpoint answer 503 and a refresh only shows the "web service is off" notice, while existing web approvals lapse at the moment it is switched off; with it on, Settings gains an authorized-web-clients list showing IP, host / client role, approval time and last activity per entry, each revocable on its own. This round Windows is at 1.0.5, macOS stays on 0.1.90, Linux stays on 0.1.82, and the CLI and source packages stay on 0.1.76.

- The Settings dialog widens to 1120 pixels, and forms no longer collapse onto two lines when you switch sections
- Contrast and saturation are gone from appearance, leaving theme, font size and interface language
- Ending a command ends only its own process tree, so Word documents you have open are no longer closed
- With the web service off, the root page and the credential endpoint return 503 and existing web approvals lapse immediately
- Settings gains an authorized-web-clients list: IP, role, approval time and last activity, each entry revocable on its own

## [1.0.3] - 2026-11-24

1.0.3 fixes one thing: with Settings → Web service switched on, the browser has to show the same interface as the window. The switch arrived in 1.0.0 with routing that pointed at the desktop build, but the installer still shipped the old output — that build handed the root path to the phone panel, so a browser on the PC opened the panel instead of the window with its sessions, approvals and settings. The three now line up: the desktop web service and `pilot serve` serve the same renderer build, with the root page, `/assets/*` and `doc.html` byte-for-byte identical, and only a mobile client carrying a pairing credential is redirected to the phone panel, so a desktop browser stays on the desktop UI even with that same link. Where an old Service Worker was still in control it kept answering the root path from its cached phone shell, so the entry script now unregisters it, clears the caches and reloads once — no manual cache clearing. The fix ships in both the desktop installer and the CLI server mode, so the two are no longer separate styles. This round Windows is at 1.0.3, macOS stays on 0.1.90, Linux stays on 0.1.82, and the CLI and source packages stay on 0.1.76.

- Settings → Web service: the root path a browser opens is the desktop window's own interface, no longer the phone pairing panel
- Same source as `pilot serve`: the root page, `/assets/*` and `doc.html` are byte-for-byte identical on both
- Only a mobile client carrying a pairing credential goes to the phone panel; a desktop browser stays on the desktop UI with that same link
- When an old Service Worker is in control it is unregistered, the caches are cleared and the page reloads once, with no manual browser cache clearing

## [1.0.2] - 2026-11-24

1.0.2 splits sending mail into two separate questions: which mailbox sends it, and which events do. Settings used to have a single Send reflection emails switch, with the address, the SMTP user name and the sender as three fields that all had to hold the same address, and no notification other than the reflection report could ever be delivered. The page now has exactly one address field — it is the recipient, the SMTP login and the sender at once, which is the same as mailing yourself — and picking one of 15 common providers (QQ, 163, Gmail, Outlook and others) fills in the server, port and encryption for you. What gets sent moved to its own Notification settings section: one master switch plus an event list ordered by usefulness, where task finished, run failed, waiting for approval, pairing request, module self-check and reflection report can each be ticked; switching the master off sends nothing at all and never backfills what was missed. Sending never blocks the main flow, each event is delivered once, and a global rate limit keeps a failing loop from flooding the mailbox. Upgrading only inherits the old reflection-email choice, so an old switch left on does not silently enable task-finished mail. This round Windows is at 1.0.2, macOS stays on 0.1.90, Linux stays on 0.1.82, and the CLI and source packages stay on 0.1.76.

- Settings → Mailbox: one address field only — it is the recipient, the SMTP login and the sender
- 15 provider presets fill in the SMTP server, port and encryption, with a custom option for anything else
- Settings → Notifications: one master switch plus tickable events (task finished, run failed, waiting for approval, pairing request, module self-check, reflection report)
- Sending never blocks the main flow: a serial queue, one delivery per event and a global rate limit
- Upgrading inherits only the old reflection-email choice and leaves the master switch off by default

## [1.0.1] - 2026-11-23

1.0.1 fixes the places where a run turned out to be wasted only after it finished. In an interrupted or compacted session an assistant turn can carry tool_calls with no matching result, and the provider rejects the whole request with a 400 — so every later "continue" failed the same way. The gap is now closed at the one point every request passes through: a missing result is written as an explicit ERROR, an orphan result whose call is gone is dropped, and the history is no longer poisoned. The recovery bar also stops saying one sentence for every failure: it tells apart a key / balance / model-permission problem, an exhausted step budget and a network drop; for a config failure the primary button is Open settings and auto-continue stops (a replay cannot change the answer, it only spends the same tokens again), and the bar shows the step the run stopped at plus how much of the plan is done, so resuming no longer means rereading the workspace. When steps or tokens run low the model gets one close-out reminder first, so the run ends with what is done, what is left and the next concrete action instead of hitting the cap and leaving one error line. This round Windows is at 1.0.1, macOS stays on 0.1.90, Linux stays on 0.1.82, and the CLI and source packages stay on 0.1.76.

- Every request now has its tool_calls paired with results before it is sent: a missing result becomes an ERROR, an orphan result is dropped, and an interrupted or compacted session no longer ends in a 400
- The recovery bar tells config, step-budget and network failures apart; a config failure makes Open settings the primary button and stops auto-continue
- A config failure names the key, the balance or the model permission, while the provider's own wording stays in the tooltip
- The recovery bar shows the step the run stopped at and how much of the plan is done, so resuming does not need a reread of the workspace
- When steps or tokens run low the model is asked to close out first: what is done, what is left, and the first next action

## [1.0.0] - 2026-11-23

1.0.0 is the first stable release of the desktop app and closes two gaps. Settings now has a web-service switch: with it on, a browser can reach the same Pilot from a phone, tablet or another machine. It does not start a second implementation — it starts the CompanionServer the command line pilot serve runs, serving the very interface the window renders, with a /bridge WebSocket that calls the same IPC table, so sessions, approvals and settings in the browser match the window exactly. The port is configurable (46831 by default), a busy port is reported as a hint to change it in Settings instead of failing silently, and switching it off stops the listener. The full-autonomy tier gets its last piece: git_status / git_diff / git_log accept repo=<absolute path> for repositories outside the workspace, and read_file, list_directory, search_files, get_file_info and project_map only advertise the widened path inside that tier, while the privacy deny still refuses those paths. Moving the version from 0.1.x to 1.0.0 only marks the desktop app as stable; feature-wise it continues the previous release. This round Windows is at 1.0.0, macOS stays on 0.1.90, Linux stays on 0.1.82, and the CLI and source packages stay on 0.1.76.

- Settings → web service: with it on a browser reaches the same Pilot, the port is configurable (46831 by default), and a busy port asks you to change it
- The browser and the window share one interface and one IPC table (/bridge), so sessions, approvals and settings match — it is not a second implementation
- In the full-autonomy tier git_status / git_diff / git_log accept repo=<absolute path> and read tools may leave the workspace, while privacy paths are still refused
- The move to 1.0.0 marks the desktop app as stable; macOS stays on 0.1.90, Linux on 0.1.82, and the CLI and source packages on 0.1.76

## [0.1.91] - 2026-11-23

0.1.91 turns plugins from subprocesses that only answer when called into capabilities the agent can actually use, and the browser console becomes the same interface as the desktop app. The tools, settings and triggers blocks in a plugin manifest now reach the runtime: when a plugin declares tools, its tools show up in the agent tool table and the tools panel with their source labelled, and the model can call them directly — each call is still checked against the permissions and limits in the manifest; when a plugin declares settings, the plugins page renders a config form for them and changes apply immediately instead of hand-editing JSON; when a plugin declares triggers, it no longer waits to be called — timer triggers (every N minutes or daily at a set time) and event triggers (session finished, task failed) are scheduled by the host, missed windows are not backfilled, and concurrent triggers collapse into one run. Three built-in plugins work out of the box: API health check probes the addresses in its config — check one address on demand, or let it sweep every configured address every 30 minutes and notify you on failure; snippet lookup stores commands, prompts and error remedies as snippets and retrieves them by keyword, counting hits and pruning the least-used ones past the limit every 4 hours; work log records what each run finished so you can look back at recent entries, checks daily at 18:00 whether today has an entry and nudges you if not, and its tags, entry count and reminder time are editable on the plugins page. The plugins page also gains a plugin assistant: describe what you need in one sentence and it writes the manifest and code into the plugin directory and tells you it is installed — when validation fails it shows the raw error so you can keep iterating. This release also wires the self-optimisation loop into the interface: the supervisor merges run records, health checks, source-structure self-inspection and reflection reports into one score-ranked list of problems, each with a reason and a suggested action; only after you explicitly enable auto-apply will it open a session inside the guardrails to fix one — off by default, with a 24-hour cap on automated sessions and instruction length, and problems filed manually or already touched within 24 hours never enter the automatic queue. The browser console is no longer a separate lightweight panel: once pilot serve is running, the browser shows the very same rendered build as the desktop app, bridged to the main process over WebSocket, so sessions, files, tools, plugins and settings all work there; scanning the QR code from the phone still lands on the phone-optimised panel instead of loading the desktop layout. Server mode gains two roles: on the same machine the host user has everything, while a client user joining with allow client keeps data in a separate users/client directory, cannot see host sessions or files, sees the billing and upgrade entries hidden, and cannot send batch commands. This round Windows is at 0.1.91, macOS stays on 0.1.90, Linux stays on 0.1.82, and the CLI and source packages stay on 0.1.76.

- A plugin manifest’s tools / settings / triggers now reach the runtime: tools enter the agent tool table, settings render a form, triggers are scheduled by the host
- Three built-in plugins install in one click: API health check, snippet lookup and work log, each with timer triggers and settings
- Plugin assistant: describe the need in one sentence and it writes the manifest and code, echoing the raw error when validation fails
- Self-optimisation loop: the supervisor ranks the problems worth fixing and can open a session to fix one inside the guardrails (off by default)
- The browser console reuses the desktop renderer build: after pilot serve, the browser shows the same interface as the desktop app
- Two roles in server mode: host user and client user, with client data kept in a separate users/client directory

## [0.1.89] - 2026-11-22

0.1.89 stops the settings dialog from jumping, makes a new model resource easy to fill in, and lets the Mac build update itself. The dialog used to size itself to its content — model resources is a long section and notifications is a single row — so switching groups made it grow and shrink and dragged the whole window with it, and the scrollbar appearing or disappearing shifted the cards sideways by 10px. The height is now locked to the window height minus 70px, capped at 820px, and the content area always reserves the scrollbar width, so all eight groups leave the frame and every card exactly where they were. Adding a model resource moved to the top of the list: the button inserts a blank card as the first row and outlines it, scrolls back to the top and puts the caret in the name field, so there is no more scrolling to the end to fill it in, and the outline clears as soon as you start typing. The macOS side is the bigger half of this release: checking for updates used to be unavailable on a Mac, because the updater only knew the Windows exe and read just the one top-level link in the release manifest, so the macOS build was never even looked at. Each macOS platform entry now carries its own update block pointing at a zip (a running app cannot install a dmg, but a zip can replace the bundle wholesale), and platform entries now carry their own version, so a macOS build can ship ahead of Windows without either side comparing against the wrong number. Downloads reuse the block-level delta already used on Windows: the new zip is compared block by block against the previous zip kept on disk and only the changed blocks are fetched, so every update after the first is usually a few MB instead of a 130 MB full package. The archive is verified against the SHA-256 in the manifest, expanded with ditto into a temporary folder on the same volume (keeping symlinks and permissions), checked against the version the bundle reports, then handed to a small script that runs after Pilot quits and atomically replaces the .app — backing up the old bundle first, rolling back if the swap fails, and reopening Pilot on success. If Pilot runs from a mounted dmg or the install folder is not writable, it says so and asks you to move the app into Applications instead of failing silently. Windows and macOS both ship 0.1.89 this round, Linux stays on 0.1.82, and the CLI and source packages stay on 0.1.76; the first hop from 0.1.82 to 0.1.89 still needs a manual dmg install, because the old version has no zip for the delta to work from.

- The settings dialog keeps one height and always reserves the scrollbar, so switching groups no longer makes it jump
- Adding a model resource inserts it at the top of the list and focuses the name field
- macOS 12+ (Intel and Apple Silicon) can finally update in place, instead of 'unsupported'
- Updates download a zip and apply block-level deltas, so later updates transfer only the changed blocks
- The new bundle is checksum-verified, staged on the same volume, swapped in after Pilot quits, and rolled back automatically if the swap fails
- Running from a mounted dmg or a non-writable install folder is reported clearly instead of failing silently
- Windows and macOS both ship 0.1.89 this round, Linux stays on 0.1.82, and the first macOS update still needs a manual dmg install

## [0.1.81] - 2026-11-21

This release fixes why a session could grind through hundreds of steps without finishing, and both causes live in the context layer.
